# Reconciliation Architecture

This document provides a detailed explanation of the **Reconciliation Engine** within the Agent Commerce Gateway (ACG). It addresses a critical requirement for production-grade distributed systems: *handling failures when external webhooks do not arrive.* 

While the primary data flow relies on reactive webhooks (Razorpay $\rightarrow$ ACG) for speed, the network is fundamentally unreliable. Webhooks can be dropped due to timeouts, crashes, or network partitions. The Reconciliation Engine is an **active polling fallback** that ensures eventually consistent state without duplicating business logic.

---

## 1. Glossary of Technical Terms

- **PSP (Payment Service Provider):** External gateway, specifically Razorpay in this context.
- **Dropped Webhook:** A scenario where the PSP successfully processes an event (like payment authorization) but the notification HTTP request to the Gateway fails to arrive or is dropped.
- **Reconciliation Cron Job:** A scheduled background process that actively audits the database for anomalies (stuck transactions) and synchronizes state with the PSP.
- **Stuck Intent:** A `PaymentIntent` that has been in an intermediate state (e.g., `PSP_INITIATED`, `UNCERTAIN`) longer than expected, indicating a potential dropped message.
- **Synthesized Event:** A mock webhook payload generated by the Reconciler to safely inject a polled PSP state back into the standard event pipeline.
- **Idempotency:** A property guaranteeing that if the Reconciler and the Webhook process the exact same transaction simultaneously, the system state remains consistent and double-actions (like double-captures) are prevented.

---

## 2. Process Flow & Data Movement

The reconciler runs on a detached background loop, separate from standard HTTP traffic.

### Step 1: Anomaly Detection (Sweep)
1. The **Cron Job** wakes up every 60–90 seconds.
2. It executes a database query looking for `PaymentIntents` where:
   - `status` is `PSP_INITIATED`, `PSP_AUTHORIZED`, or `UNCERTAIN`.
   - `createdAt` or `updatedAt` is older than a specific threshold (e.g., 2 minutes).
3. These intents represent users who clicked "Pay" but whose final outcome never reached the gateway.

### Step 2: Direct PSP Verification (Active Polling)
4. For each stuck intent, the system issues a direct outbound HTTP `GET` request to Razorpay to fetch the true, current state of the order and its payments.
   - **HTTP Request:** `GET https://api.razorpay.com/v1/orders/{pspOrderId}/payments`
5. The gateway derives the definitive state of the transaction from Razorpay's response (`authorized`, `captured`, `failed`, or `null`).

### Step 3: Branching & Resolution

The reconciler takes action based on what Razorpay reports:

#### Scenario A: Payment is `authorized` at PSP, but local is `PSP_INITIATED`
*What happened: The user paid, but the `payment.authorized` webhook dropped.*
- The Reconciler constructs a **Synthesized Event Payload** that mirrors a standard webhook payload.
- It pushes this payload into the **shared `handlePaymentAuthorized` pipeline**.
- **Crucial Architecture Decision:** By reusing the exact same function the webhook router uses, the transaction still passes through the **Pre-Capture Money-Action Gate** (`runPreCaptureGate`). Inventory and velocity checks are enforced exactly as if the webhook had arrived normally.
- If the Gate approves, the Reconciler issues the API call to `capture` the funds.

#### Scenario B: Payment is `captured` at PSP, but local is stuck
*What happened: The capture succeeded, but the subsequent database update crashed, or the `payment.captured` webhook dropped.*
- The Reconciler marks the local database intent as `PSP_SUCCEEDED`.
- It appends a `RECONCILED` event to the Append-Only Audit Trail.
- It triggers the **Fulfillment Saga** (Outbox write) to ensure the merchant and agent are still notified of the success.

#### Scenario C: Payment is `failed` or abandoned
*What happened: User closed the Razorpay modal or the payment declined, but the failure webhook dropped.*
- The Reconciler marks the local database intent as `PSP_FAILED` or `FAILED`.
- It executes a **Compensating Action**: releases all Redis distributed inventory locks associated with the cart.

## 3. Architecture Decisions & Security Measures

### 1. Unified Logic Path (No Duplication)
Instead of writing separate capture logic for the webhook handler and the reconciler, the reconciler acts as an event synthesizer. It feeds data into the same `handlePaymentAuthorized` function. This guarantees that security rules (Money-Action Gate) cannot be bypassed simply because a transaction was reconciled rather than webhooked.

### 2. Idempotent Execution via Correlation IDs
Because the Reconciler and delayed Webhooks could theoretically process the same event concurrently:
- The Reconciler generates a unique `correlationId` (e.g., `reconciler:{intent.id}`).
- Database constraints and the `TransactionEvent` log ensure that if the transaction transitions to `PSP_SUCCEEDED` from one thread, the other thread safely no-ops. Razorpay's API is also idempotent on capture calls (capturing an already captured payment returns a safe error).

### 3. The `UNCERTAIN` State
If an API call to capture funds throws an unexpected network error (e.g., `ECONNRESET`), the gateway cannot know if the capture succeeded at the PSP.
- Instead of guessing `FAILED` (which could lead to lost money) or `SUCCEEDED` (which could lead to unfulfilled goods), the system marks the intent as `UNCERTAIN`.
- The Reconciler specifically targets `UNCERTAIN` intents on its next sweep, resolving the ambiguity by asking the PSP for the absolute truth.

### 4. Handling Concurrency and DB Issues
By offloading retry logic to the Reconciliation loop and Outbox workers, the primary web threads are freed from managing long-polling or retry states. If the database locks up temporarily and a webhook write fails, the webhook returns a 500 error. The PSP might retry, but even if it gives up, the Reconciler guarantees the transaction will be discovered and processed correctly.
